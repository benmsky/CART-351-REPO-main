WEEK 2: SEPT 21st

This week we started Python, and honestly I'm still a little confused by it. Coming from HTML, CSS and JavaScript, some of it feels familiar, like variables, if/else and comparisons, but the syntax is different enough that I kept second-guessing myself. No curly braces, no semicolons, and the indentation actually matters, which took some getting used to. I've also been sick this week, basically on "bedrest" (okay, that's a bit of an exaggeration), so I've actually had a lot of time to sit down and focus on this. To get myself moving, I ended up watching a few beginner Python videos on YouTube before starting the exercise. Seeing someone type things out and run them step by step helped more than just reading the slides, and it gave me the push I needed to actually open VS Code and start. From the Python Foundations I lecture, the string methods stood out the most, things like len(), .find(), .strip() and .upper(). Exercise 1 was basically a bunch of small puzzles using these, and running the file and comparing my output to the expected output made it feel less intimidating. One thing that tripped me up was that dividing with / always gives a decimal in Python 3... I also looked at the Real Python page on dynamic typing linked in the lecture. The idea that a variable doesn't have a fixed type and Python just figures it out when the code runs made sense to me after using type() in the exercise, even if I still don't fully get where that becomes a problem in bigger projects. I'm not fully comfortable with Python yet, but breaking it into small tasks seems to be helping... I'm praying I can retain what I'm learning.

WEEK 3: SEPT 28th

This week was the second part of Exercise 1, and I think Python is maybe starting to click a little? I'm not totally sure yet. Part A was all about lists, and a lot of it built on the string stuff from last week. Indexes starting at 0 I already knew from JavaScript, but slicing took me a while. If I understand it right, greek[1:4] gives you the second through fourth items because the end number isn't included... I had to try it a few times before I believed it. Using a negative number like -2 to grab the last two items seems really handy, though I'm not sure I'd remember that on my own. The task that confused me the most was sorting. I first thought I could just print a sorted version of the list, but the next task expected the sorted list with "radishes" added to the end, so I think I had to use .sort() because it actually changes the list itself? It's a small thing but it kind of showed me that each task affects the next one, which I didn't really expect. .split() and .join() made a bit more sense, turning "9/18/25" into "9-18-25" helped me see how you can break a string apart and glue it back together, at least I think that's the idea. Part B was the fun part, but also the part where I felt the most lost. We used the requests package to pull planet info from the Star Wars API, and then the Rich library to print it out as a coloured table in the terminal. Seeing real data come back from a website and show up as an actual table was kind of cool, even if I don't fully understand everything happening behind the scenes. It took me a bit to figure out that the API only sends 10 planets at a time, so to get the same 14 planets as the example I ended up asking for each planet by its number in a loop. I'm honestly not sure if that's the "right" way to do it, but it worked. Going back through the Python Foundations II lecture helped me make a bit more sense of what I was actually doing in Part B. Dictionaries seem a lot like JavaScript objects, where instead of looking things up by an index you use a key, so something like planet["name"] or planet["population"]. I think what clicked for me is that response.json() takes the JSON the API sends back and turns it into a Python dictionary, which is why I could just grab the values by name. The nested part still kind of melts my brain though. The lecture's shopping example, shopping_rev['vegetables']['orange'][0], where you read it backwards to figure out what you're getting, makes sense when I read it slowly, but I don't think I could write one from scratch yet without some trial and error. The URL section was also useful, I never really thought about a URL as having separate parts like the scheme, host, path and query string. Apparently a lot of learning an API is just figuring out how to build the right URL, which kind of explains why swapi.dev/api/planets/1/ gives you Tatooine. I also didn't know that most APIs need a key, so I'm a little nervous for when we get to the weather API. The params= thing in requests, where you pass a dictionary and it builds the query string for you, sounds handy but I haven't actually tried it myself yet, so I'm not 100% sure I get it. On the side, I tried to clean up my repository a bit. There was an extra old .git folder hiding inside my project folder that I think was confusing VS Code, so I moved it out and added the new exercises to my homepage so everything is hopefully in one place. I feel a little more comfortable than last week, but I still second-guess myself a lot... I'm hoping it keeps sinking in the more I practice.
